# What to Cook (Android)

Add the ingredients you have and get recipe ideas generated by AI. Native Android app built with
Kotlin and Jetpack Compose. No ads, no analytics, text-only AI (no photo scanning).

> "What to Cook" is a placeholder name. Change `app_name` in
> `app/src/main/res/values/strings.xml` and it updates everywhere.

---

## Tech stack

| Area | Choice |
| --- | --- |
| UI | Kotlin, Jetpack Compose, Material 3, single activity, Navigation Compose |
| Architecture | MVVM, `ViewModel` + `StateFlow`, Hilt |
| Network | Retrofit + OkHttp + kotlinx.serialization |
| Local data | Room (pantry, recipes, shopping list), DataStore (theme, onboarding flag, recipe options) |
| Auth | Guest sessions issued by your backend and stored in Turso (no Firebase, no sign-up) |
| Payments | Google Play Billing Library 7 (one subscription, two base plans) |
| Build | Gradle Kotlin DSL + version catalog (`gradle/libs.versions.toml`), minSdk 26, targetSdk 35 |
| Animation | Compose animation APIs only (no Lottie, no animation files) |

## Run it

1. Open the project folder in **Android Studio** (Ladybug 2024.2 or newer, bundled JDK 17+ is fine).
2. Let Gradle sync. The Gradle wrapper (8.11.1) is included.
3. Run the `app` configuration on a device or emulator (API 26+).

Out of the box `USE_FAKE_BACKEND=true`, so every screen works with sample recipes and a local
7-per-week counter and a local guest session. You don't need a backend for this.

Unit tests (from a terminal): `./gradlew testDebugUnitTest`

## Configuration

All values are read from `local.properties` first (gitignored), then `gradle.properties`, and end up in
`BuildConfig`. Copy `local.properties.example` to `local.properties` and edit:

| Key | Purpose | Default |
| --- | --- | --- |
| `BACKEND_BASE_URL` | HTTPS base URL of your backend (trailing slash added if missing) | `https://api.example.com/` |
| `USE_FAKE_BACKEND` | `true` = `FakeRecipeRepository` / `FakeUsageRepository`, `false` = real backend | `true` |
| `PRIVACY_URL` | Opened from Account > Privacy & terms and from the paywall | placeholder |
| `TERMS_URL` | Same as above | placeholder |
| `SUPPORT_EMAIL` | Help & feedback opens a `mailto:` to this address | placeholder |

**The app never contains secrets.** There is no Turso token, database URL, or AI API key anywhere in
the client. All AI calls and usage counting go through your backend.

## Sign-in (guest sessions in Turso)

There is no Firebase and no sign-up screen. Every install is a guest, like anonymous auth:

1. On first launch the app calls `POST /auth/guest` (no auth header).
2. Your backend creates a user row and a session row in **Turso** and returns `{ userId, token }`.
3. The app stores the token in its own DataStore file (`auth`) and sends
   `Authorization: Bearer <token>` on every other request.
4. If the server answers **401**, the app throws that session away, creates a new guest session
   once, and retries the request (`TokenRefreshAuthenticator`).
5. Sign out clears the token on the device and starts a fresh guest. Delete account calls
   `DELETE /account` first, then does the same.

Backend side (the app never sees any of this):

- Secrets on the server only: `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, your AI key, and a Google Play
  service account for purchase checks.
- Make the token a long random value (32+ bytes) and store only its **SHA-256 hash** in Turso.
- On each request: hash the bearer token, look it up in `sessions`, and use that `user_id`.
  Unknown token: return 401.
- Rate-limit `POST /auth/guest` per IP, since anyone can call it.

```sql
CREATE TABLE users (
  id             TEXT PRIMARY KEY,          -- the userId you return
  plan           TEXT NOT NULL DEFAULT 'free',
  pro_expires_at INTEGER,                   -- epoch ms
  created_at     INTEGER NOT NULL
);

CREATE TABLE sessions (
  token_hash   TEXT PRIMARY KEY,            -- sha256(token), never the raw token
  user_id      TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at   INTEGER NOT NULL,
  last_seen_at INTEGER
);

CREATE TABLE usage (
  user_id    TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  week_start INTEGER NOT NULL,              -- epoch ms, e.g. Monday 00:00 UTC
  used       INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (user_id, week_start)
);

CREATE TABLE purchases (
  purchase_token TEXT PRIMARY KEY,
  user_id        TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  product_id     TEXT NOT NULL,
  expires_at     INTEGER,
  created_at     INTEGER NOT NULL
);
```

Count usage in one statement so two quick taps can't both take the last free recipe:
`UPDATE usage SET used = used + 1 WHERE user_id = ? AND week_start = ? AND used < ? RETURNING used`
(insert the week's row first with `INSERT OR IGNORE`). If no row comes back, answer 429.

## Backend contract

Every request except `POST /auth/guest` sends `Authorization: Bearer <session token>`.

```
POST /auth/guest         <- no Authorization header
  200:  { userId: String, token: String }

POST /recipe
  body: { ingredients: [String], diet: String?, timeMinutes: Int?, equipment: [String]?,
          cuisine: String?, allowMissing: Int }
  200:  { recipes: [{ id, title, summary, timeMinutes, servings,
                      ingredients: [{ name, quantity, unit, inPantry }],
                      steps: [String], missing: [String],
                      substitutions: [{ missing, swap }] }],
          usage: { used, limit, resetsAt } }
  429:  { error: "limit_reached", resetsAt: Long }

GET /usage
  200:  { plan: "free" | "pro", used: Int, limit: Int, resetsAt: Long }

POST /verify-purchase
  body: { purchaseToken, productId }
  200:  { plan, expiresAt }

DELETE /account          <- also needed (Google Play requires in-app account deletion)
  2xx:  any body or none. Delete the user and all their rows (sessions, usage, purchases).
```

Notes for the server:

- `resetsAt` may be epoch **seconds or milliseconds**; the client accepts both.
- `quantity` may be a JSON string or number.
- Discover moods are sent through the existing fields (e.g. "High protein" -> `diet: "high-protein"`,
  "One pan" -> `equipment: ["one pan"]`, "Comfort food" -> `cuisine: "comfort food"`).
  See `domain/RecipePresets.kt`.
- When the pantry is empty (or the user picks "Anything" on Discover) the client sends
  `ingredients: []` with a high `allowMissing`.
- Free plan: 7 recipes per week, used however the user likes. The server owns the count and the
  reset date. The client shows "X of 7 recipes left this week" and opens the paywall (with the reset
  date) on 429 or when the cached count is already at 0.
- Error handling in the UI: 401/403, 429, timeouts (408/504 and socket timeouts), no network, and
  other server errors each get their own message and a retry button.

## Google Play Billing

1. In Play Console create **one subscription** (default ID `what_to_cook_pro`) with **two base plans**:
   `pro-monthly` (1 month) and `pro-yearly` (1 year). Set your prices there ($1.99 / $14.99).
2. If you use different IDs, change them in **one place**:
   `app/src/main/java/com/whattocook/app/data/billing/BillingProducts.kt`.
3. Prices are never hardcoded. The paywall shows the localized `formattedPrice` from Play and
   computes the "Save N%" badge from Play's real prices.
4. Billing only works for builds installed from Play (internal testing track is fine) with a
   license-tester account.
5. Flow: purchase -> client sends `purchaseToken` to `POST /verify-purchase` -> backend validates it with
   the Google Play Developer API and returns the plan -> client acknowledges the purchase.
   "Restore purchases" re-verifies active subscriptions.

## Fonts

Fonts are bundled in `app/src/main/res/font` (no runtime downloads):
**DM Serif Display** for screen titles and **DM Sans** (Regular, Medium, SemiBold, Bold) for everything
else. Both are SIL Open Font License; license texts are in `docs/font-licenses/`. To swap fonts, replace
the `.ttf` files (keep the names) or edit `ui/theme/Type.kt`.

## Permissions

Only `INTERNET` and `com.android.vending.BILLING`. The manifest also strips `ACCESS_NETWORK_STATE` and
`AD_ID` that libraries could merge in. If a future library genuinely needs network state, delete that
`tools:node="remove"` entry.

## Design notes

- Dark theme is the default (`ThemeMode.DEFAULT` in `domain/model/ThemeMode.kt`). Users can pick
  System / Light / Dark in Account; the choice is stored in DataStore.
- Both color schemes live in `ui/theme/Color.kt` and `Theme.kt`.
- Onboarding shows once (DataStore flag set on finish or skip) and can be reopened from
  Account > View onboarding. It respects the system "Remove animations" setting.
